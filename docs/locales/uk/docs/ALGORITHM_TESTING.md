# Тестування алгоритму та внесок

Алгоритми MeshMill мають зробити складну геометрію керованою, зберігаючи їхні ефекти видимими,
вимірюваний і оборотний до застосування результату.

## Довідкові світильники

Використовуйте обидві пакетні версії геометрії складеного зразка:

- `samples/sample-scan.stl` — це менший стандартний модуль Git для рутинної розробки, автоматизований
  перевірки та вивчення елементів керування.
- `samples/original-scan.stl` — це повний інструмент Git LFS для роботи з великими файлами, надлишкових шарів,
  нерівномірна щільність, перекриття та продуктивність роботи.

Надлишкові та щільні області є навмисними тестовими характеристиками. Тест може бути спрямований на них, але
не варто припускати, що кожна поверхня, що перекривається, є одноразовою. Додайте компактні синтетичні сітки, коли a
зміна потребує відомої межі, кривизни, топології, щільності або інваріанта перекриття.

## Контрольний список для порівняння

Для зміни алгоритму або параметра запишіть:

- Версія MeshMill або фіксація;
- фіксатор введення та контрольна сума;
- алгоритм, попередні налаштування якості, цільові та додаткові налаштування;
- кількість вихідних і отриманих трикутників і вершин;
- відсоток зменшення, розміри та дрейф розмірів;
- витрачений час і пікова пам'ять, коли продуктивність є важливою;
- скріншоти тих самих збережених переглядів і режимів відображення;
- видимі межі, отвори, самоперетини, перекриття або зміни спотворення;
- незалежно від того, отримано результат від операції з цілою сіткою чи лише для вибору.

Порівняйте з поточною поведінкою на тій же цілі, а не лише з іншим попереднім налаштуванням з a
різна кількість вихідних даних. Перевірте затінені, щільність, каркасні та вершинні дисплеї, де це можливо.

## Керівництво з приймання

Зміна оптимізації повинна уникати неочікуваних змін розмірів, очевидної інверсії поверхні,
тріщини між обробленими областями, втрата значущих меж і великі регресії якості на a
подібна кількість вихідних даних. Зміни, орієнтовані на щільність, повинні продемонструвати, що вилучена концентрація була
не мають корисної кривизни або топології.

Результати продуктивності мають визначати процесор, об’єм пам’яті, графічне обладнання, операційну систему
систему, розмір вхідних даних і те, чи дані вже кешувалися. Структурна перевірка та скріншоти
підтримує перевірку, але не замінює перевірку співавторами, знайомими з геометрією джерела.

## Регресійні тести

Віддавайте перевагу детермінованим тестам із явними допусками. Тримайте нові прилади достатньо малими для нормального Git,
документувати своє походження та ліцензію, а також використовувати синтетичну геометрію, коли справжні вихідні дані непотрібні.
Тести повинні охоплювати скасування та відновлення стану, коли операція може змінити геометрію.
